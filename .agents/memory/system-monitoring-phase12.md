---
name: System Monitoring (Phase 12) architecture
description: Where platform health data comes from for the admin System Monitoring page, and the container-filesystem disk-usage gotcha.
---

- `AdminMonitoring.tsx` existed as unwired dead code (comment said "Phase 9") before it was wired into `Admin.tsx`'s tab list — same unwired-admin-dead-code pattern as other phases; always check for a pre-built-but-orphaned component before writing a new one.
- Its expected shape came first (`PlatformHealth` interface), so the backend `/admin/platform-health` endpoint was built to match that shape exactly rather than inventing a new contract, then extended with fields the existing component didn't have (disk, imap, cronJobs, runningJobs, failedJobs, recentErrors).
- No cron/queue library (BullMQ, node-cron) exists in this repo — all "background jobs" are `setInterval` loops started in api-server `app.ts` (Campaign Watchdog, Bounce Scanner, Gmail Draft Sync). They had no last-run/last-error tracking; added a tiny additive `lib/monitoring-state.ts` module with `touchCronStart/Success/Error` calls wrapped around each loop body — does not change any existing control flow (activeJobs Map, retry logic), purely observational.
- "IMAP health" is not a live per-request IMAP connection test (too slow/costly to run on every health poll) — it's inferred from the Bounce Scanner cron's last successful run recency (operational if succeeded within ~3 min) and its last error, since the bounce scanner *is* the IMAP consumer.
- "Running Jobs" = `campaignsTable` rows with status `sending`/`cooling_down`, not the in-memory `activeJobs` Map in `campaigns.ts` — simpler and already reflects real DB state without needing new introspection exports.
- `fs.statfsSync('/')` reports the container's overlay filesystem as ~4MB total in this environment (sandboxed/virtualized fs, not the real host disk) — this is not a code bug. The disk-usage UI must treat any `totalGb < 0.5` as "not available in this environment" rather than showing a misleadingly tiny percentage; in a real deployed VM this same code will report real numbers.
- Reused existing endpoints instead of duplicating: mailbox test-connection/test-imap, campaign resume, and per-lead retry already existed. Added only two new admin actions because they were genuinely missing: `POST /admin/monitoring/run-bounce-scan` (manual trigger, previously only automatic) and `POST /admin/monitoring/queue/:id/retry` + `retry-all` (bulk requeue of failed `email_queue` rows — no such endpoint existed before, only per-lead retry scoped to a campaign+lead).
